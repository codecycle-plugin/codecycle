# /codecycle:setup

## Zweck
codecycle in diesem Projekt einrichten oder die Einrichtung ändern. Du bist der **Bauleiter**. Mechanisches (Ordner, Werkzeug-Kopie, Ausschlüsse, Hooks, Selbsttest) machst du ohne Rückfrage; gefragt wird vor Eingriffen außerhalb des Projekts oder schwer Umkehrbarem (Node oder Git installieren, `git init`, `master` umbenennen, fremder `core.hooksPath`) und einmal gesammelt zu den Standards (Schritt 5), im Format „Fragen an den Nutzer“ des Workflow-Skills.

## Voraussetzungen
- Plugin-Ordner (für Pfade in gelesenen Dateien): `${CLAUDE_PLUGIN_ROOT}`
- Git-Projekt, Node.js ab Version 24. Optional: ein Code-Graph, entweder code-review-graph (uv) **oder** CodeGraph (`@colbymchenry/codegraph`); für die Prüfung von Oberflächen das Playwright-Plugin (`playwright@claude-plugins-official`) mit Google Chrome; `codecycle selftest` prüft beides.

## Schritte
1. Lies `${CLAUDE_PLUGIN_ROOT}/skills/workflow/SKILL.md`.
2. **Voraussetzungen prüfen (vor allem anderen, ohne Agent; direkt nach dem Lesen der Workflow-Anleitung):** Führe `git --version`, `node --version` und `git rev-parse --is-inside-work-tree` aus.
   - **Node fehlt oder ist älter als Version 24:** Hier nicht weitermachen; ohne Node läuft das Projekt-Werkzeug `codecycle` nicht, und der Bau bliebe stehen (der Mod, die Bautafel und die Agenten-Leiste laufen auch ohne Node). Stelle das Betriebssystem fest und nenne genau einen Befehl:
     - Windows: `winget install OpenJS.NodeJS.LTS`
     - macOS: `brew install node` (ohne Homebrew: Installer von nodejs.org)
     - Linux: über die Paketverwaltung der Distribution oder `nvm install 24`
     Biete an, den Befehl auszuführen, und tu es **nur nach ausdrücklicher Zustimmung** (er installiert Software auf dem Gerät). Danach `node --version` erneut. Meldet die Shell trotz erfolgreicher Installation noch „not found“ oder die alte Version, kennt die laufende Sitzung den neuen Pfad nicht: Bitte den Nutzer, **Claude Code neu zu starten** und `/codecycle:setup` noch einmal aufzurufen, und halte hier an.
   - **Git fehlt:** genauso (Windows `winget install Git.Git`, macOS `xcode-select --install`, Linux Paketverwaltung).
   - **Kein Git-Repo:** frage, ob `git init -b main` ausgeführt werden soll; ohne Repo nicht weitermachen.
   - **Hauptbranch:** Vorgabe ist `main`. Ein Repo ohne Commit bekommt `main` (`git init -b main` bzw. `git symbolic-ref HEAD refs/heads/main`) und ohne Rückfrage einen ersten, leeren Commit (`git commit --allow-empty -m "Projektstart"`); ohne ihn kann eine Aufgabe ihren Branch nicht gegen den Hauptbranch prüfen. Gibt es schon einen Hauptbranch `master`, biete mit Begründung das Umbenennen an („`main` ist heute der Standard, auch auf GitHub; die Umbenennung ändert nur den lokalen Branch“): `git branch -m master main`, nur lokal. Weise darauf hin, dass ein Remote (`git push -u origin main`, Standardbranch dort umstellen) sowie offene Branches und Worktrees angepasst werden müssen. Nie automatisch; bei Nein bleibt `master`, die Vorlage trägt dann `mainBranch: master` ein (`tool/config-template.ts` fragt Git nach dem tatsächlichen Hauptbranch). Danach prüfen, dass `mainBranch` in `.codecycle/tool.config.json` stimmt.
   - Erst wenn Git und Node ab 24 da sind, weiter mit Schritt 3.
3. **Projekt verstehen:**
   - **Bestehendes Projekt:** Starte `codecycle:setup`; er schreibt `.claude/codecycle.md` nach `${CLAUDE_PLUGIN_ROOT}/skills/workflow/templates/project.md` (Berichtspfad ohne Aufgabe: `.codecycle/tmp/reports/setup.md`) und schlägt den Doku-Aufbau vor. Aus dem Abschnitt „So verstehe ich das Projekt“ seines Berichts spiegelst du in wenigen Punkten zurück, wie ihr das Projekt verstanden habt; der Nutzer korrigiert (Antwort in Schritt 5 mit).
   - **Leeres Projekt** (kein Code): kein Erkunden, kein Agent. Du schreibst `.claude/codecycle.md` selbst nach der Vorlage, mit dem, was das Brainstorming der ersten Aufgabe ergeben hat (Sprache, Werkzeuge); Befehle stehen auf „nicht vorhanden“, bis die erste Aufgabe Grundgerüst und Testbefehl baut und den Testbefehl dort und in `.codecycle/tool.config.json` nachträgt (Plan der Aufgabe). Kommt die Einrichtung nicht aus dem Brainstorming, verweise darauf: Die erste Aufgabe mit `/codecycle:new` klärt Sprache und Werkzeuge.
   - Gibt es `.claude/codecycle.md` schon, ist das eine Änderung: frage, was geändert werden soll.
4. **Projekt-Werkzeug, ohne Rückfrage** (du legst die Kopie selbst an, kein Agentenlauf):
   - Führe `codecycle install-tool` aus (der Starter nimmt dafür immer den Plugin-Kern). Es legt `.codecycle/tool/` mit `lib/` darin und `githooks/` an, ohne Tests; wiederholbar. Zum Aktualisieren nach einem Plugin-Update (oder nach einem frischen Klon ohne `.codecycle/`) gibt es `/codecycle:update`: Plugin, Kopie, Konfiguration, Hooks und guard-Grundlage in einem Lauf. Kein eigenes Kopieren. Scheitert der Selbsttest danach an den Importpfaden, starte `codecycle:toolsmith`.
   - **`.codecycle/tool.config.json`:** `codecycle install-tool` legt sie als Vorlage an, wenn sie fehlt (nie überschreibt es eine vorhandene; bei einer vorhandenen ergänzt `codecycle install-tool --update-config` nur fehlende Felder wie `junit`): Version des Werkzeugs, `mainBranch`, Befehle aus den `package.json`-Skripten (`test`, `lint`, `format`), `graph.provider` `none`, wenn kein Graph-Werkzeug erkannt wird. Bei `node --test` trägt die Vorlage zusätzlich die JUnit-Reporter und `junit` ein (Voraussetzung für die Testzahl-Regel von `codecycle guard`). **Prüfe die Vorlage und passe sie an**, bevor du weitermachst; `codecycle:toolsmith` kann das übernehmen. Format:
     ```json
     {
       "version": "0.1.0",
       "mainBranch": "main",
       "commands": { "test": "npm test", "lint": null, "format": null },
       "graph": { "provider": "none" },
       "junit": ".codecycle/tmp/junit.xml"
     }
     ```
     `version` (Pflicht, Text) und `commands` (Pflicht) müssen stehen; `junit` ist optional (relativer Pfad im Projekt, ohne `..`). Ein Befehl `null` heißt „im Projekt nicht vorhanden“, ein **fehlender** Eintrag „nicht eingerichtet“ (der Selbsttest meldet ihn als Fehler), ein leerer Text ist ungültig. Weitere Befehle: `testFilter` (mit `{filter}`), `testFull`, `testAffected` (mit `{files}`), `server` (übernimmt `install-tool` aus der Zeile `server:` unter „Befehle“ in `.claude/codecycle.md`; fehlt er in einer vorhandenen Konfiguration, ergänzt ihn `codecycle install-tool --update-config`). `serverTemp` (optional): `{ "env": "<Umgebungsvariable>", "file": "<Dateiname, Standard daten>" }` = Name der Umgebungsvariable, über die der Server seine Datendatei liest; damit startet `codecycle server --temp` den Server für die Prüfer mit einer Wegwerf-Datei. Oder `{ "ohneDaten": true }` = der Server speichert nichts; `--temp` startet ihn dann ohne Variable. Lies den Wert aus der Projektbeschreibung (Zeile `Wegwerf-Daten`, vom Nutzer bestätigt): Umgebungsvariable → `env`, „ohne Daten“ → `ohneDaten`, „keine Wegwerf-Möglichkeit“ → Eintrag bleibt weg (die Oberfläche bleibt dann ungeprüft). `graph.provider`: `auto` | `code-review-graph` | `codegraph` | `none`; `auto` nimmt den Anbieter, dessen Index im Projekt liegt. Frage, welcher Graph genutzt werden soll, falls beide oder keiner vorhanden sind; einen Graphen installieren nur nach Rückfrage.
   - **Lokal halten:** Führe `codecycle exclude` aus (idempotent): trägt `.claude/`, `.codecycle/` und `.githooks/` in `.git/info/exclude` des Hauptrepos ein. Bei Ablage „teilen“ (Standard, Schritt 5) führe stattdessen `codecycle exclude --share` aus: dann bleibt `.claude/codecycle.md` versionierbar, ausgeschlossen werden nur `.claude/settings.local.json`, `.codecycle/` und `.githooks/` (ein früherer pauschaler `.claude/`-Eintrag in `.git/info/exclude` muss dann entfernt werden; der Befehl weist darauf hin). Du nimmst zuerst den Standard „teilen“ (`--share`); wählt der Nutzer in Schritt 5 „lokal“, wiederholst du den Aufruf ohne Option. Danach setzt `hooks install` `core.hooksPath` **absolut** auf den `.githooks`-Ordner des Hauptordners, weil nicht versionierte Hooks in Worktrees sonst fehlen. Also `exclude` **vor** `hooks install`.
   - **Fehlt ein Prüfwerkzeug** (Test, Lint, Format) in einem bestehenden Projekt: schlage in Schritt 5 ein minimales vor (Empfehlung und Gegenargument); bei Ja wird es eine eigene kleine Aufgabe (`/codecycle:new`). Im leeren Projekt gehören Grundgerüst und Testbefehl in den Plan der ersten Aufgabe. Werkzeug-Änderungen gibt der Nutzer immer frei.
   - Führe danach `codecycle selftest` aus (prüft Werkzeug, Konfiguration, Graph, Hooks, Kopie; bei einer Oberfläche auch Playwright-Plugin, Google Chrome, zweiten Playwright-Server und Serverbefehl). Scheitert er, melde es und biete den Werkzeugmeister an. Bei einer Oberfläche: dem Nutzer das Ergebnis der Browser-Prüfung und die Abhilfe-Befehle nennen (Hinweise, kein Fehlschlag; installieren macht er). In `.claude/codecycle.md` trägst du es nicht ein; dort steht nur Dauerhaftes, kein Zustand und keine Umgebungsangaben.
   - **Hooks, ohne Rückfrage** (erst nach gültiger Konfiguration und nach `codecycle exclude`; ohne gültige `.codecycle/tool.config.json` bricht `hooks install` mit Meldung ab, weil der Graph-Anbieter aus ihr in die Hooks geschrieben wird): Führe `codecycle hooks install` aus (legt `.githooks/` mit Graph-Aktualisierung und gestuftem Pre-Commit an, setzt `core.hooksPath`, ergänzt vorhandene Hooks statt sie zu ersetzen; mit `--dry-run` zeigt es vorher, was passiert). Zeigt `core.hooksPath` schon auf etwas anderes (husky, lint-staged), ändert das Werkzeug nichts: Das ist eine Frage an den Nutzer (Empfehlung und Gegenargument). `codecycle hooks status` prüft den Stand. Meldet er (oder der Selbsttest) einen Hook als „veraltet“, etwa nach einer Änderung der Konfiguration oder des Plugins, führe `codecycle hooks install` erneut aus.
5. **Ein Block „So richte ich es ein“** (eine Nachricht, kurze Punkte, Standards schon eingetragen), dann **eine** Frage, ob etwas anders sein soll:
   - Sprache der Agenten-Ausgaben (Standard Deutsch).
   - **Ablage der Aufgaben-Doku** (`docs/codecycle/`), echte Entscheidung: „a) Empfehlung: teilen“ (im Repo committet, geht auf andere Geräte mit), „b) Dagegen spricht: …“ (Aufgabenordner landen im Verlauf des Projekts; wer das nicht will, wählt lokal, Eintrag in `.git/info/exclude`). Wechsel von teilen auf lokal heißt `git rm --cached`; vorher nachfragen, weil andere Personen die Dateien beim nächsten `git pull` verlieren. Werkzeug und Konfiguration (`.codecycle/`, `.githooks/`, bei Ablage „lokal“ auch `.claude/`) bleiben lokal; `.codecycle/tmp/` sowieso.
   - Doku-Aufbau nach dem Vorschlag des Einrichters (Wurzel-`CLAUDE.md` kurz, Verweise als Pfad in Backticks statt `@`-Import, Bereichs-`CLAUDE.md`, Architektur unter `docs/architecture/`); steht unter „Doku-Aufbau“.
   - **`.gitignore`**, nur ergänzen, nie überschreiben (`codecycle exclude [--share] --gitignore` für die übernommenen Einträge): `.codecycle/` ausschließen (Werkzeug-Kopie und lokale Ablagen, die jedes Gerät selbst erzeugt), `.claude/settings.local.json` ausschließen (persönliche Einstellungen), `.claude/codecycle.md` bei Ablage „teilen“ committen (Risikobereiche und Schalter gehen auf ein anderes Gerät mit; `.claude/` darf deshalb nicht pauschal ausgeschlossen sein).
   - **`.gitattributes`:** `docs/codecycle/** text eol=lf` (nur die Aufgabenordner; verhindert die Warnungen „LF will be replaced by CRLF“ unter Windows) über `codecycle exclude --gitattributes` (legt an oder ergänzt, überschreibt nie).
   - **Profil ohne Mod:** `sparsam` / `großzügig` / `extrem` (ändert nur die Modelle), gespeichert in `~/.claude/codecycle/profile.json` im Format `{ "profil": "sparsam" }` (Schlüssel `sparsam`, `grosszuegig`, `extrem`). Mit Mod stammt das Profil aus dem Mod-Speicher.
   - **Schalter:** Standardwerte aus der Schalter-Tabelle im Workflow-Skill (darunter `assume-and-continue`, Standard an: Agenten arbeiten bei Unklarheit mit markierter Annahme weiter); Änderungen im Abschnitt „Schalter“ von `.claude/codecycle.md`.
   - Dazu, falls zutreffend: fehlendes Prüfwerkzeug (Schritt 4), fremder `core.hooksPath` (Schritt 4).
6. **Eigene Frage, ohne Empfehlung:**
   - **Kennzeichnung durch Claude** (**ohne Empfehlung**; der Nutzer entscheidet, später änderbar unter `attribution` in `.claude/settings.json` oder mit erneutem Setup): Was soll in Commits und Pull Requests stehen? Zeige je Antwort ein kurzes Beispiel, wie das Ende einer Commit-Nachricht aussieht.
     - (a) Urheberzeile und Sitzungslink (Standard von Claude Code): Zeile `Co-Authored-By: Claude <noreply@anthropic.com>` am Ende jedes Commits, Hinweis „Generated with Claude Code“ in Pull Requests, Zeile `Claude-Session: <Link>` in Cloud- und Remote-Control-Sitzungen. Belegt, dass und in welcher Sitzung Claude mitgearbeitet hat; den Link öffnet nur das eigene Konto, solange die Sitzung nicht öffentlich gestellt ist.
     - (b) Nur den Sitzungslink, keine Urheberzeile.
     - (c) Nichts: die Commit-Nachricht endet mit dem Text selbst.
     - Führe die Antwort in `.claude/settings.json` des Projekts **zusammen** (Datei lesen, bestehende Schlüssel erhalten, nur `attribution` setzen; fehlt die Datei, anlegen), immer mit allen drei Schlüsseln, weil eine globale Einstellung sonst durchschlagen kann: (a) `"attribution": { "commit": "Co-Authored-By: Claude <noreply@anthropic.com>", "pr": "🤖 Generated with [Claude Code](https://claude.com/claude-code)", "sessionUrl": true }`, (b) `{ "commit": "", "pr": "", "sessionUrl": true }`, (c) `{ "commit": "", "pr": "", "sessionUrl": false }`.
7. Antworten umsetzen; was der Nutzer nicht geändert hat, gilt mit dem Standard („Empfehlung übernommen“).
8. Fasse das Ergebnis kurz zusammen (angelegte Dateien, Selbsttest) und frage bei Ablage „teilen“ als einfache Frage, ob committet werden soll.

## Ergebnis
`.claude/codecycle.md`, `.codecycle/tool/` (mit `lib/`), `.codecycle/tool.config.json`, `.githooks/`, ein gespeichertes Profil, Graph-Anbieter in der Konfiguration; Selbsttest grün.

## Nächster Schritt
`/codecycle:new <Beschreibung>`; kommt die Einrichtung aus dem Brainstorming, zurück zu `/codecycle:new`, „1. Entwurf“. Im leeren Projekt gehören Grundgerüst und Testbefehl in den Plan der ersten Aufgabe.
